01 / WHAT

Skill 到底是什么？

Skill = 一个 Markdown 文件，让 AI 在特定场景下按照你验证过的方式工作。

不是 Prompt，不是插件，不是代码 — 是结构化的经验沉淀。

对比PromptSkill
生命周期一次性持久复用
知识你当场想到的验证过的规则
触发你手动写自动路由匹配
进化不会越用越准
核心理论：为什么 Skill 有效

Context > Prompt

给 AI 看什么，比怎么问更重要

Gotchas > Instructions

踩坑规则比操作步骤价值高 10 倍

Structure > Length

结构化的 200 字 > 散装的 2000 字

本质：Skill 是把你大脑里的隐性知识（踩过的坑、验证的规则、偏好）显性化为 AI 可读的文件。模型本身有能力，Skill 给它方向。

02 / ANATOMY

Skill 的完整解剖

--- name: my-skill-name description: "触发词描述，AI 靠这个路由" --- # 一句话定位 这个 Skill 做什么、不做什么。 ## Gotchas (踩坑规则，优先级最高) 1. 绝对不能 XXX 2. 必须先 YYY 再 ZZZ 3. 用词规范：A 不说 B ## Workflow Phase 1 → Phase 2 → Phase 3 ## Phase 1: [阶段名] 目标: ... 输入: ... 输出: ... 停止条件: ... ## References (按需加载) 详细规范、模板、示例

六大要素详解

要素作用重要度
name唯一标识，用于引用必填
description触发路由 — AI 靠它决定是否加载必填
Gotchas踩坑规则，防止重复犯错最高价值
Workflow分阶段执行，带停止条件高
References详细规范，按需加载不占 token中
Scripts可执行脚本赋能可选

关键原则：description 里写触发词而不是描述功能。写"用户说做个demo/给老板看时激活"，而不是"这是一个demo生成工具"。

Gotchas 是灵魂：模型有通用能力，但不知道你踩过什么坑。Gotchas = 你交的学费，让 AI 免费复用。

LEVEL 1

手写 Skill

99% 的人只需要掌握这一步

找重复工作
→
让 AI 做一遍
→
反馈变规则
→
固化成 Skill

手写不是"从零编程"。是把你已经验证的工作方式，翻译成 AI 能读懂的结构化文件。你需要的是业务理解，不是技术能力。

03 / L1 实操

四步手搓法（保姆级）

Step 1：找出重复最多的事

问自己：过去一周，我跟 AI 说了几次一样的话？哪件事我每次都要重新解释？

Step 2：让 AI 做一遍，记录全程

不要给指令。正常交互，观察它哪里做对了、哪里做错了。每个"不对，应该是..."就是一条 Gotcha。

Step 3：反馈沉淀成规则

把所有"不对"翻译成正面规则。不是"不要用签约"，而是"支付场景统一用'开通/绑定'"。

Step 4：组装成 Skill 文件

用 skill-creator 引导，或直接写 Markdown。放入 .claude/skills/ 目录。

实战案例：Demo Generator

痛点：给客户做 Demo 要半天，找设计排期要一周

支付场景禁用"签约"，使用"开通/绑定"
用户认为"签约"太正式 → 来自第2次反馈
内部算法名（三力模型等）不在 Demo 中出现
外部受众不该看到内部概念 → 来自第3次反馈
"智能赋能""一站式""无缝衔接"出现即失败
AI-slop 文案零容忍 → 来自第1次反馈
所有数据必须由用户提供，禁止编造真实感数据
演示数据一旦被当真会造成误导 → 来自第5次反馈

效果：麦当劳 Demo 20min | 海尔 Demo 15min | 方案 PPT 10min ← 之前各需半天

05 / COMBO

Skill 组合 = 团队协作

单个 Skill 搞不定复杂任务 — 让多个各司其职：

demo-generator ← 主控 ├―― frontend-design ← 视觉规范 ├―― frontend-slides ← PPT 生成 ├―― grill-me ← 拷打需求 ├―― problem-clarity ← 问题评判 └―― prd-critic ← 方案评估

六阶段工作流：拷打需求 → 锁定视觉 → 生成 Demo → 自检迭代 → 反向拷打 → 一源多版

组合的三个原则

1. 每个 Skill 只做一件事
单一职责 — 一个 Skill 解决一类问题
2. 通过 description 触发词路由
主控 Skill 不直接引用子 Skill，靠关键词匹配
3. Gotchas 不重复，各管各的
避免规则冲突 — 视觉规范的坑放在视觉 Skill 里

方案 PPT3h10min18x

07 / NUWA

女娲蒸馏流程

Phase 0 入口分流 ├ 明确人名 → 直接蒸馏 └ 模糊需求 → 诊断推荐 → 再蒸馏 Phase 0.5 深度调研（6 Agent 并行） → 著作与系统思考 → 长对话与即兴思考 → 碎片表达与风格 DNA → 他者视角与批评 → 决策记录与行动 → 人物时间线 Phase 1 提炼思维框架 Phase 2 生成可运行 Skill

输出物：一个可执行的 Skill 文件，调用时以该人的思维方式来分析问题、做决策、给建议。

蒸馏对象与素材

蒸馏谁需要什么素材
你自己文章/决策备忘录/会议录音/聊天记录
行业专家公开著作/访谈/演讲/播客
历史人物著作/传记/书信/决策记录
虚构角色小说原文/影视剧本

提取维度

维度内容
心智模型看问题的框架和角度
决策启发式快速判断的直觉规则
表达 DNA用词习惯、节奏、比喻偏好
反模式绝对不会做的事
诚实边界承认做不到什么

伦理提醒："蒸馏"他人需要获得本人授权。蒸馏公开人物的公开信息用于个人学习可以，商业用途需谨慎。

08 / MISTAKES

常见错误 & 避坑指南

错误 1：Skill 写太长（>2000 行）
占满 context window，模型反而变笨。Skill 应该精炼，详细内容放 References 按需加载。
错误 2：把操作步骤当 Gotchas
"第一步打开页面" 不是 Gotcha。"打开页面后必须等 3 秒再操作否则会白屏" 才是。
错误 3：Description 写功能描述而非触发词
"一个生成 Demo 的工具" 无法路由。"用户说做个demo/给老板看/给客户演时激活" 才能被 AI 匹配到。
错误 4：一个 Skill 做太多事
既做需求分析又做代码生成又做测试 = 哪个都做不好。拆成多个组合使用。
错误 5：装太多 Skill 不管理
50 个 Skill 互相冲突，AI 不知道听谁的。保持 10-15 个高频使用的就够。

写好 Skill 的黄金法则

法则 1：Gotchas 第一优先

写 Skill 的 80% 时间应该花在整理踩坑规则上，这是模型不知道的独家知识。

法则 2：停止条件必须明确

每个 Phase 要有 exit criteria，否则模型会无限发散。"输出 PRD 后停止等待反馈" 比 "尽量写好" 有效 100 倍。

法则 3：从真实反馈中提取

别脑补规则。每条 Gotcha 都应该对应一次"不对，应该是..."的真实经历。

法则 4：定期迭代

Skill 不是写完就不动了。每 2 周 review 一次，删除过时的，补充新发现的。

法则 5：先测试再固化

新 Skill 先在对话中试 3 次，确认效果好再放进 skills 目录。

10 / DECIDE

我该选哪种方式？

这件事你重复做过吗？ ├ 没有 → 别写 Skill，正常对话就好 └ 做过 3+ 次 → ├ 你能清楚描述规则？ │ ├ 能 → L1 手写（最可控） │ └ 说不清 → L2 Hermes 观察提取 └ 想复制某人的思维？ └ → L3 女娲蒸馏

80/20 原则：80% 的人只需要 L1 手写。把你重复最多的 3 件事写成 Skill，效率就能翻倍。不要追求"自动蒸馏"的炫酷，先把手写练好。

SUMMARY

核心结论 & 行动清单

01

Skill = 经验文件化

把重复的话变成 .md 文件
AI 自动加载，你不再重复

02

Gotchas 是灵魂

你踩的坑 = 最高价值知识
写 Skill 80% 时间花在这

03

Context > Prompt

给什么比怎么问更重要
Skill 解决的是 context 问题

本周行动

  • 找出重复最多的 1 件事
  • 让 AI 做一遍，记录 5 条反馈
  • 写出你的第一个 Skill
  • 用 3 次，迭代 Gotchas

判断标准

  • AI 放大判断力，不替代判断力
  • 半天→半小时后，时间花在"判断对不对"
  • 先做再想：想法→Demo→PRD
  • 验证是最快的规划
